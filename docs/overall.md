# LuaLoom 总体开发文档

> 状态：基线设计 · 2026-10-24

## 目标

为 .NET 提供 Lua 5.3 / 5.4 与 C# 的双向桥接库。对外 API 借鉴 xLua 的使用习惯以降低迁移成本；内部按职责拆分，核心不依赖任何游戏引擎。

解决的问题：.NET 项目想用 Lua 做脚本与热更新时，通常要在成熟方案与自行绑定之间取舍。xLua 面向 Unity 场景、功能覆盖面广，是这一领域被广泛使用的实现；如果宿主是纯 .NET、希望核心保持小而职责清晰，则缺少直接可用的选择。LuaLoom 把这一层做成可独立引用、可审查的库。

成功与否看五条，全部可判定：

1. `samples/LuaLoom.Sample` 在 Windows x64 上跑通六条主流程，进程退出码为 `0`。
2. 纯值类型 struct 与枚举在 Lua↔C# 间往返 100 万次，`GC.GetAllocatedBytesForCurrentThread` 增量为 `0`。
3. C# 回调抛异常、Lua 执行报错、参数类型不匹配三类错误发生后，`lua_gettop` 与进入调用前相等。
4. 核心库、生成器、示例在未引用任何 Unity 程序集的环境中构建通过。
5. 对 Lua 调 C# 的成员访问，同一组用例在「生成代码」与「反射兜底」两条路径下执行，结果一致。

非目标：Unity 及其他引擎适配、热补丁、LuaJIT、脚本签名、资源版本与增量分发、iOS/Android/WebGL、Windows arm64 与 Linux arm64。

## 功能概述

主流程逐条列出，每条是「输入 → 产出」：

1. **初始化**：`new LuaEnv(options)` → 一个可用的 Lua 虚拟机（版本由构建决定）；`options` 指定库加载器、日志、初始 `package.path`。
2. **执行脚本**：`DoString(code, chunkName)` 编译并运行 → 返回 `object[]`；脚本内的 `require` 走 loader 链。`env.Global.Get<T>(name)` 用于读取全局值。
3. **Lua 调 C#**：`CS.Namespace.Type(...)`、`obj:Method(...)`、`obj.Field = v` → 返回 Lua 值或抛 `LuaException`。
4. **C# 调 Lua**：`env.Global.Get<TDelegate>("name")` 或 `LuaTable.Get<TKey,TValue>` → 得到可调用的委托、值或句柄。
5. **生成绑定**：`lua-loom-gen generate --config lua-loom.json` → 一组 `.g.cs`；启动时调用 `LuaBindings.Register(env)` 把类型绑定注册进环境，之后 `CS.*` 走生成路径。
6. **诊断**：`env.StartProfile()` / `env.StopProfile()` / `env.MemorySnapshot()` → 文本报告。

## 重大困难与主要原理

风险点三个，各写触发条件与应对原理：

**1. 栈平衡与异常安全**

Lua 的 C API 是栈式的，一次调用里 push 几个、pop 几个、出错时栈剩什么，全靠调用方自己保证。栈操作一旦分散在翻译器、回调注册和生成代码里，任一分支提前 return 或抛异常都可能破坏栈，症状是后续调用错位，很难定位。

触发条件：C# 回调抛异常、Lua 脚本执行报错、参数类型不匹配、`longjmp` 与 .NET 异常交错。

应对原理：栈操作集中在 `LuaApi`（P/Invoke）、`LuaMarshal`（编解码）与 `LuaBinding`（生成代码原语）三层；所有跨边界入口统一套 `LuaStackGuard`，进入时记录 `top`，`finally` 中 `lua_settop` 恢复；C API 的 `lua_pcall` 返回值统一转成 `LuaException`，不允许异常穿过原生栈帧。C# 侧的表访问（`LuaTable.Get/Set`）与生成代码的方法入口也走 `lua_pcall` 包裹，Lua 元方法报错不会以未保护错误终止进程。

**2. 值类型零 GC 传递**

引用语义的默认实现要把 struct 装箱成对象再挂到 userdata，每传一次产生一次分配，高频调用下 GC 压力不可接受。

适用条件：struct 只含值类型字段（可嵌套）、枚举、基本类型数组；含引用字段时没有内联或装箱回退，直接抛 `NotSupportedException`（调用方改用类或自定义 marshaler）。

应对原理：生成期按字段布局生成直接解包/打包代码，运行时把 struct 拆成若干标量压栈，不构造中间对象；枚举按底层整数传递；参数与返回值都走同一套生成的强类型路径。判定标准就是 100 万次往返零分配，跑不出来即视为未实现。

**3. 生成路径与反射路径一致**

生成路径与反射兜底如果各自演进、缺少统一契约，容易出现行为差异；但反射兜底必须保留，否则改一个类型没重跑生成就无法运行。

触发条件：重载解析、默认参数、`out`/`ref`、枚举与字符串互转、可变参数、泛型方法。

应对原理：两条路径共用同一份 marshal 契约与同一组用例；生成代码只负责「按已知类型走最短路径」，语义判定全部落在共用的解析器里。测试用同一组用例跑两遍并比对结果，出现差异即阻断。反射路径默认在开发期开启、发布期关闭。

## 特殊规则与限制

| 规则 | 违反后果 |
| :-- | :-- |
| 运行时只依赖 `lualoom.dll` 与托管库；Roslyn 等构建期依赖不得进运行时 | 包体膨胀，使用方的运行环境被编译器依赖绑死 |
| Lua 状态只在创建它的线程使用，跨线程调用抛异常 | 数据竞争，Lua 内部状态损坏且无法恢复 |
| `LuaApi`、`LuaMarshal`、`LuaBinding` 之外的模块不自行拼装栈序列；直接调用 `LuaApi` 时必须已有栈守卫 | 栈失衡无法局部定位，review 失效 |
| 生成代码带 `<auto-generated/>` 头且不得手改，CI 重跑比对 | 手改逻辑在下次生成时被覆盖 |
| Lua 版本在构建期二选一（5.3.6 / 5.4.9），版本差异只能出现在 `LuaRuntimeProfile` | 版本判断散落各处，新增版本时遗漏调用点 |
| 支持范围：Windows x64（本地验证）、Linux x64 与 macOS arm64（CI 工作流已配置） | 其他平台需补原生构建、RID 加载与 CI，否则 `DllNotFound` |
| 不引入 Unity 程序集引用 | 核心无法在其他宿主复用，脱离 Unity 的目标失效 |

依赖清单：原生 Lua 5.3.6 / 5.4.9（MIT，构建时二选一）；生成器用 Microsoft.CodeAnalysis.CSharp 与 System.Reflection.MetadataLoadContext（仅构建期）；测试用 xUnit（仅测试）。不引入 Mono.Cecil。

## 实现方式

### 技术方案

分层与数据流：

```
Lua 脚本
   ↕ lua_*（C API，栈式）
LuaApi         P/Invoke 一对一映射，唯一出现 DllImport 的地方
   ↕
LuaMarshal     push/pop、类型编解码、引用注册表、错误转换
   ↕
LuaEnv         生命周期、加载器、GC、Tick、公共 API
   ↕
Interop        句柄方法补全（Cast）、DelegateBridge、InterfaceBridge、反射兜底
   ↕
生成代码       按类型的强类型路径（由 CodeGen 产出）
```

关键选型与理由：

- **P/Invoke 直接绑定 `lualoom.dll`**，不加 C 中间层。理由：Lua 的 C API 稳定，中间层只会再叠一层栈语义，反而扩大 review 面积。库名固定，查找路径由 `ILibraryLoader` 决定；版本差异收敛到 `LuaRuntimeProfile`。
- **句柄用「注册表 id + 所属环境标识」**，`LuaTable`/`LuaFunction`/`LuaReference` 实现 `IDisposable`，释放即 `luaL_unref`；`Tick()` 只回收漏网句柄并记日志。理由：把引用生命周期从周期性回收改为作用域结束即释放，减少「忘记回收」这一类问题。
- **生成器用 Roslyn 读元数据、产出 C# 源码**，不做 IL 改写。理由：产物可读、可断点、可入库审阅；同时避免引入 Mono.Cecil。
- **反射兜底用缓存的 `MethodInfo` 调用**，不生成 `DynamicMethod`。理由：兜底路径只在开发期使用，实现简单优先，性能由生成路径负责。
- **配置只有一份 JSON**，生成器读取后把结果注册进运行时缓存。理由：多种配置入口并存时容易产生优先级与覆盖问题，只留一个来源更可控。

被否选项：

- 用 C++/CLI 或 C 中间层封装 Lua：跨平台构建更复杂，收益仅是少写 P/Invoke 声明，不值。
- 生成 IL 而非 C#：产物不可读，调试困难，与「可审查」目标冲突。
- 句柄用 `SafeHandle`：Lua 引用不是 OS 句柄，`SafeHandle` 的 `ReleaseHandle` 在 GC 终结线程执行，会违反单线程约束。

### 界面方案

本库无图形界面。对外呈现为三层：

- **公共 API**：`LuaEnv`、`LuaTable`、`LuaFunction`、`LuaReference`、`LuaException`、`ILibraryLoader`、`ITypeMarshaler`；另有生成代码专用的 `LuaBinding`。公共类型数量在模块文档中逐一定义，不额外暴露实现类型。
- **命令行**：`lua-loom-gen`，子命令 `generate` 与 `check`，参数 `--config` 与可选 `--coverage`，成功退出码 `0`，失败打印诊断并返回非 `0`。
- **示例程序**：`samples/LuaLoom.Sample`，控制台输出每步结果与耗时，末尾打印 `ALL PASSED`。

## 模块划分

| 编号 | 模块 | 职责 | 对外契约 | 依赖 | 顺序 |
| :-- | :-- | :-- | :-- | :-- | :-- |
| M001 | native-binding | P/Invoke 声明、原生库加载、栈守卫、C API 错误转异常 | 公共：`ILibraryLoader`、`LuaCSFunction`、`LuaException`、`LuaLibraryNotFoundException`；`internal`：`LuaApi`、`LuaStackGuard` | 无 | 1 |
| M002 | value-marshal | 类型映射、push/pop 编解码、引用注册表、句柄类型、生成代码原语 | 公共：`LuaReference`/`LuaTable`/`LuaFunction`、`ITypeMarshaler`、`LuaBinding`；`internal`：`LuaMarshal`、`LuaReferenceTable` | M001 | 2 |
| M003 | vm-runtime | 虚拟机生命周期、加载器与 `require`、GC 控制、`Tick` | 公共：`LuaEnv`、`LuaEnvOptions`、`ScriptLoader`、`GcMode`、`LogLevel` | M001 M002 | 3 |
| M004 | interop-bridge | delegate 桥、interface 桥、`Cast<T>`、`CS.*` 与反射兜底 | 公共：`ILuaDelegateInvoker`、`LuaTypeBinding`、`LuaInterfaceProxy`；`internal`：`Interop` | M002 M003 | 4 |
| M005 | codegen | 配置模型、Roslyn 生成器、CLI、增量与校验 | 契约：CLI `lua-loom-gen` 与 JSON 配置格式 | M002 的运行时契约 | 5 |
| M006 | diagnostics | 函数耗时统计、内存快照 | 公共：`LuaEnv.StartProfile`、`StopProfile`、`MemorySnapshot` | M003 | 6 |

模块数量六个，在 3–8 的范围内。M005 与 M004 可并行，但生成代码依赖 M004 的公共契约，故顺序排在其后。M003 初始化末尾调用 M004 的 `Interop.Install`，两者同属 `LuaLoom.Core`，不构成编译依赖。

## 构建与集成

环境要求：

- .NET SDK 8.0 或更高（本机已验证：SDK 10.0.303 + 运行时 8.0.32）
- CMake 3.20 以上
- Visual Studio 2022 的 C++ 工具链（Windows x64）

首次构建，在 `812-LuaLoom/` 下依次执行：

```powershell
pwsh scripts/fetch-lua.ps1
pwsh scripts/build-native.ps1
dotnet build samples/LuaLoom.Sample.Types -c Release
dotnet run --project src/LuaLoom.Cli -c Release -- generate --config lua-loom.json
dotnet build LuaLoom.sln -c Release
```

切换 Lua 5.3 时，给三个命令加版本参数：`pwsh scripts/fetch-lua.ps1 -Version 53`、`pwsh scripts/build-native.ps1 -Version 53`、`dotnet build ... -p:LuaVersion=53`。

生成本地绑定必须先编译 `LuaLoom.Sample.Types`，因为生成器的输入是它的程序集；`samples/LuaLoom.Sample/Generated/` 已入库，日常构建不需要重复生成。

- `fetch-lua.ps1 -Version <53|54|55>` 从 `scripts/lua-versions.json` 取 URL 与 SHA-256，解压到 `build/<source>/`。
- `build-native.ps1 -Version <53|54|55>` 调用 CMake 生成 `artifacts/native/<rid>/lualoom.*`（Windows 为 `.dll`，Linux 为 `.so`，macOS 为 `.dylib`）。
- `dotnet build` 产出 `artifacts/bin/`；路径布局由 `Directory.Build.props` 的 `ArtifactsPath` 固定，`LuaLoom.Native.csproj` 把 `artifacts/native/<rid>/lualoom.*` 复制到输出目录，并随项目引用传递到测试与示例的输出目录。

测试与示例：

```powershell
dotnet test LuaLoom.sln -c Release
dotnet run --project samples/LuaLoom.Sample -c Release
```

生成绑定：

```powershell
dotnet run --project src/LuaLoom.Cli -c Release -- generate --config lua-loom.json
dotnet run --project src/LuaLoom.Cli -c Release -- check --config lua-loom.json
```

清理：

```powershell
dotnet clean LuaLoom.sln -c Release
Remove-Item -Recurse -Force artifacts, build
```

版本规则：SemVer，`0.x` 阶段允许破坏性变更，版本号只在 `Directory.Build.props` 的 `Version` 属性改一处；程序集版本与包版本同源。

## 测试总体设计

| 层级 | 工具 | 覆盖范围 | 结果判读 |
| :-- | :-- | :-- | :-- |
| 单元 | xUnit | `LuaMarshal` 编解码、`LuaStackGuard`、类型映射表、重载解析器、配置模型 | 全部通过；每个异常分支至少一条用例 |
| 模块集成 | xUnit + 真实 `lualoom.dll` | M002、M003、M004 每个公共入口一条正常用例、一条异常用例 | 全部通过；栈顶检查通过 |
| 端到端 | 示例程序 | 六条主流程；生成绑定在构建阶段验证，其余在运行时验证；Lua 调 C# 的成员访问在生成与反射两条路径下各跑一遍 | 退出码 `0`，输出 `ALL PASSED` |

性能基准尚未建立；值类型零分配目前由 `MarshalTests` 在编解码层直接验证。

异常覆盖按四类补齐：空集合与边界值（空表、空字符串、`nil` 参数）、非法输入（越界索引、错误类型、`chunk` 语法错误）、依赖失败（`lualoom.dll` 缺失、loader 找不到文件、原生库版本不符）、重复与并发（重复 `Dispose`、跨线程调用、重入回调）。

测试程序集通过 `InternalsVisibleTo` 访问内部原语（`LuaApi`、`LuaMarshal`），只用于验证实现细节；公共契约的验证走集成层，不用内部接口绕过。

界面走查不适用（无界面），替代为公共 API 表面检查：每个模块文档列出的公共类型必须在程序集内可见，未列出的实现类型不得 `public`。该检查目前靠人工核对，没有自动化用例。

完成判据：每条预期都有用例；栈平衡与零分配两项有客观数据；生成路径与反射路径的用例结果一致；测试失败先改用例再改实现，不得放宽断言。
